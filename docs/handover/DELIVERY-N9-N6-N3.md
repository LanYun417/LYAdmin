## 3. 验收标准修正记录（决策留档）

**产品经理原验收标准**："viewer 手敲 `/system/role` 落 **403** 而非 404。"

**实测结果**：仍落 **404**。**根因是架构决定的**（工程师发现、QA 独立确认、我复核）：
动态路由由**后端下发的已授权菜单树**生成（`admin/src/store/modules/permission.ts:231` 的 `generateRoutes(menus)` → `buildRoutes`），**未授权页根本没有注册路由** → 命中 `routes.ts` 的 catch-all 404。guard 的 403 分支对"不存在的路由"不可达。

**裁定：接受 404，修正该验收标准。** 理由：

1. 要 403，必须让前端拿到**全量路由/路径存在性**才能区分"存在但无权(403)"与"不存在(404)"，而当前前端只持有已授权子集 —— 这会**放大信息暴露**（前端即知道系统所有路由）。
2. 从安全角度，**对未授权资源返回 404 比 403 更保守**（不泄露资源存在性），是安全领域的常规做法。
3. 成本约 0.5 人日，收益仅是"错误语义更友好"；而 N3 真正的价值在 **N3-b**（403 整页刷新 → 路由跳转），已完成。
4. guard 的 `meta.permission` 校验**保留**，作为防御纵深（覆盖"权限被中途中回收而路由仍陈旧"的边角场景）。

**若后续仍想要 403**，QA 评估的最小方案是：后端增加一个**只读**「全量菜单路径」接口，前端在 catch-all 兜底处做 deny-by-catalog → 403。无"一行修复"，但比工程师最初估的"改架构"要小。
