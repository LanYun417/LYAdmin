## 2. F3 留痕覆盖率：结果与一个"宁滥毋纵"的决定

启动日志：`[AuditCoverage] 写接口 22 个，未留痕 0 个（覆盖率 100%）`
构成：users 6 + roles 4 + menus 3 + logs 1 + files 2 + gen 3 + profile 3（已排除 `/api/auth/*` 3 条与 `/api-docs`）。

**关键实现难点**：运行时枚举得到的是路由**模板**（`/api/users/:id`），而 `OPERATION_RULES` 的正则按**真实路径**写（`/^\/api\/users\/\d+$/`）——直接匹配会把**全部带参路由误报为"未留痕"**。解法是把 `:param` 展开为两个样本（`1` 数字、`test` 文本）再匹配。

**QA 挖出的方向性问题**：`any-match`（任一样本命中即算覆盖）方向偏**漏报**——
若将来有人加**字符串参数**路由（`/api/things/:slug`）却配了数字规则，`any-match` 会让它**不告警**，而真实请求 `/api/things/abc` 其实**不落审计** = 真黑洞。

**我的决定（Round 2）**：保留 `any-match`（避免 22 处误报），**追加提示级告警**——当"数字样本命中、文本样本全不命中"时输出：
`[AuditCoverage] 提示：<method> <path> 仅数字参数可留痕，请确认参数类型是否为数字`
**宁滥毋纵**：宁可多提示，不漏黑洞。当前 22 个路由参数均为数字 id，正常场景**不出现**该提示（已实测）。

- **粒度**：`dependencies`（运行时）**任何增 / 删 / 改版本** → 阻断并点名；`devDependencies` **仅告警**。

## 4. 日志治理

| 表                  | 保留期   | 理由                                                                                 |
| ------------------- | -------- | ------------------------------------------------------------------------------------ |
| `sys_http_log`      | **7 天** | 磁盘风险主源（推算 ≈8.6 GB/天 @100QPS）；我**未采纳**产品经理建议的 30 天（=258 GB） |
| `sys_operation_log` | 180 天   | 审计证据                                                                             |
| `sys_login_log`     | 180 天   | 折中                                                                                 |

- **清理机制**：分批 `DELETE ... LIMIT 1000`（批间 sleep 20ms），**弃用 TRUNCATE**（长事务锁表伤在线请求）。手动"清空所有日志"保持原实现不变。
- **调度**：复用项目自研 `logging/scheduler.ts`（`setTimeout` 自调度 + 启动补跑 + 防漂移），**00:10 触发**，避开归档任务的 00:05。**未引入 cron**（零依赖 + Windows 无 crontab）。
- **count 缓存**：`/api/logs/http` 的 `count` 加 30s TTL 进程内缓存，**键含筛选条件**（防串数），**契约不变**（仍返回精确 `total`，最多 30s 陈旧）。实测 miss 10.2ms → hit 3.4ms。
- **索引**：`sys_operation_log.created_at` 与 `sys_login_log.login_at` 原本**无索引**（QA 发现），已补（`idx_created_at` / `idx_login_at`，主理人已 `SHOW INDEX` 复核）。

### QA 的删除边界实测（最关键的一环）

| 插入时刻（相对 now） | 预期   | 实际     |
| -------------------- | ------ | -------- |
| 30 天前              | 删     | 删 ✓     |

## 5. ★QA 挖出的真实隐患（Round 2 已修）★

**`LOG_HTTP_RETENTION_DAYS=0` 会清空整张表** —— `cutoff = now - 0 = now`，而配置解析无下界校验。
**一个环境变量的笔误就能删掉 7.6 万行日志。**

**修复**：新增 `parseRetentionDays()`（`config/index.ts:44`）——非有限 / 非整数 / **≤ 0** → 拒绝并回退默认 + 打印告警；`> 3650` 天仅告警。
**验证**：10 组单元测试全 PASS（`0` / `-1` / `abc` / `1.5` / 空串 → 均回退默认值）。主理人已复核代码逻辑。

**另加紧急刹车**：`LOG_RETENTION_ENABLED`（默认 `true`），设 `false` 时不注册调度器、不清理，并打印"已禁用"。

## 6. 一个纠正旧认知的技术事实

**`sequelize.sync()` 即使 `alter: false`，也会自动补建模型里声明的「索引」。**

工程师执行 `ALTER TABLE ... ADD INDEX` 时遇到 `Duplicate key name` —— 因为用户的 3000 实例在他改完 model 后已重启，`sync` **自动把索引建好了**。他为确认还 `DROP INDEX` 再重启，索引**自动补回**。

**结论**：新增**索引**只需在 model 里声明 `indexes: [{ name, fields }]`，既有库无需手动 ALTER；但新增**列**仍需手动 ALTER（`sync` 不补列）。已写入项目长期约定。
