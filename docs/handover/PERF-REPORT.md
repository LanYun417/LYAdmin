## 3. 前端：瓶颈 → 优化 → 结果

### 3.1 定位到的瓶颈

| #      | 瓶颈                                                                                          | 量化证据                                                                                                      |
| ------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **F1** | `main.ts` 用 `app.use(BootstrapIconsPlugin)` **全局注册全部 2052 个图标**，源码实际只用 27 个 | `lib.esm-*.js` = **222 kB gzip，占首屏 JS 的 56%**，且被 `index.html` 的 `modulepreload` **放进首屏关键路径** |

| **F2** | 新建 `admin/src/utils/echarts.ts`，改 `echarts/core` + 按需 `charts`/`components`/`renderers` + `echarts.use([...])`                                                                                                                                                                  | echarts 减约 50%      |

## 4. 后端：瓶颈 → 优化 → 结果

### 4.1 定位到的瓶颈

| #      | 瓶颈                                              | 量化证据                                                                                          |
| ------ | ------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **B1** | `loadAuthUser()` **每个鉴权请求都查库，零缓存**   | 鉴权链路净开销：c=50 时 **+216 ms P95**；`/api` 5550 RPS vs 鉴权接口 235~379 RPS（**1/15~1/18**） |
| **B2** | controller 与 service **重复调用** `loadAuthUser` | `/api/auth/profile` 同一条「User+Role」查询**执行了两次**（每请求 3 条 SQL）                      |
| **B3** | `/api-docs` **每次请求都重新构建** 212 kB HTML    | c=10 P95 40.44 ms，每请求消耗约 2.9 ms 单线程 CPU                                                 |
| **B4** | SQL 日志**同步写文件**，阻塞事件循环              | `DB_LOGGING=false` 使 `/api/users` c=50 P95 **250.9 → 179.5 ms（−28.5%）**                        |

> **关键洞察**：慢 SQL Top5 全是 37 行小表的 `count(*)` 耗时 259 ms → 说明瓶颈**不是单条 SQL 慢，而是连接池（`pool.max=10`）排队**。这直接决定了"减少查询次数"（缓存）比"优化单条 SQL"更有效。

### 4.2 实施的优化

| 项     | 做法                                                                                                                                                                                         | 预期效果             |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| **B1** | 新增 `api/src/services/authCache.ts`：30 s TTL 进程内缓存 + **主动失效**（用户增改删/启停/改密/角色变更、角色增改删/授权、菜单增改删、资料/头像/改密、**登录**）；容量上限 5000 + 惰性 sweep | 鉴权接口 P95 降 50%+ |
| **B2** | `auth.service` 加 context 形参、`auth.controller`/`middlewares/auth` 复用同一份加载结果                                                                                                      | 每请求 SQL 3 → 2     |
| **B3** | `api/src/docs/index.ts` 加结果缓存（+ `clearDocsHtmlCache` 供需要时清除）                                                                                                                    | P95 40 → <5 ms       |
| **B4** | 新增 `api/src/logging/dbLogBuffer.ts`：SQL 日志改**批量缓冲 + 100 ms flush**，退出路径（SIGINT/SIGTERM/uncaughtException）先 flush 再关流                                                    | P95 −28%             |

## 6. 未达标项与遗留（如实记录）

1. **F2 echarts 未达 ≤500 kB**（实为 565 kB raw / 192 kB gzip，已降 49%）。这已是「core + 3 图表 + 3 组件 + Canvas」的下限，再降须砍 legend/tooltip/grid（会损功能）。**判定：接受现状**。
2. **B3 的 c=10 P95 未达 <5 ms**（18 ms）。c=1 已达 2.36 ms，说明 **CPU 开销已消除**，残差是 212 kB 响应体在回环上的传输开销。**后续可选**：加响应压缩（gzip 中间件）。
3. **B4 的极端终止会丢尾部日志**：`SIGKILL`/断电等**不可捕获**终止会丢最多 ~100 ms（<200 条）缓冲中的 SQL 日志。正常 `SIGINT`/`SIGTERM`/`uncaughtException` 已覆盖（先 flush 再关流）。**判定：可接受**——`logs/db` 是调试日志，审计用的 `sys_http_log` 走数据库同步写、不受影响。
4. **`/api/logs/http` 性能无提升**：原因是压测把这表从 125 行撑到 **63,065 行**，大表 `count(*)` + 排序的开销正好抵消了优化收益（复跑 3 次与基线重叠，**非优化回退**）。
   **后续建议**：① 加复合索引；② 用近似计数（如 `SHOW TABLE STATUS` 或缓存在 Redis）；③ 按日志保留策略归档（`sys_http_log` 推算 **≈8.6 GB/天 @100 QPS**，是最大磁盘风险）。
5. **B1 的进程内缓存多实例不共享**：与 `loginRateLimit` 同样的局限，集群化时需换共享存储（如 Redis）。当前单体部署够用。
6. **测量局限**（影响结论强度，需知悉）：本机 8 GB 且 API 与 MySQL **同机**、单进程无 cluster、数据集偏小（菜单 37 行 / 用户 2 行）、单次采样无多轮中位数（并发 50 时单次 RPS 波动可达 ~77%，故结论以**方向 + 区间**为准）、仅测只读 GET、未做长时间稳定性压测（短期 91.6 → 239 MB 后进入平台期，无失控增长迹象，但**不足以判定无内存泄漏**）。

5. 补最小回归测试（`node:test`，零依赖）覆盖 `authCache` 失效与权限判定 —— 缓存类改动的**最佳保险**
