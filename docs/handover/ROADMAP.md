# LYAdmin 后续开发建议路线图

> 生成日期：2026-09-24 ｜ 基线：`master @ eb5671a`
> 三条线独立产出：**产品方向**（许清楚）· **架构演进**（高见远）· **质量基建**（严过关）
> 本文件是**统一裁决后的行动清单**，三份分项建议见 §7 索引。**未改动任何源码。**

---

## 0. 先说结论

**推荐方向：开发者生产力基座**——以项目自带的 `gen` 代码生成器为北极星，把**「新增一个业务模块的端到端耗时」**作为唯一核心北极星指标。

| 阶段   | 北极星指标               | 达成标志                           |
| ------ | ------------------------ | ---------------------------------- |
| 现状   | 60~90 分钟 / 手工 5 步   | —                                  |
| 3 个月 | **≤30 分钟 / 手工 0 步** | gen 生成后自动补齐全部接线         |
| 6 个月 | **≤15 分钟**             | 模板支持关联表、导入导出、差异预览 |

**为什么是它**：`gen` 已经打通了低代码最难的部分——读 `information_schema` → 生成 7 个文件 → 自动接线 `models/index.ts` 与 `routes/index.ts`。生成物是**静态源码**，天然享受 `tsc`/`vue-tsc`/ESLint 三重校验兜底（当前实测全零告警），风险远低于运行时动态渲染。**只差"生成后自动补菜单/权限码/catalog/留痕"这最后 2 人日就能把手工作业清零。**

**不选其它两条路**：

- ❌ **继续堆通用模块**（字典、公告、任务调度……）：这些是若依类项目的标配，拼功能数量必输，且会拖散精力。
- ❌ **下沉做垂直业务**：业务代码混进基座会直接毁掉"基座"这一定位。

## 1. 三条线的核心建议（交叉后的共识）

| 线       | 一句话结论                                           | 关键依据                                                             |
| -------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| **架构** | 修 P0-1 用**方案 C（构建后别名重写）**，不动 src     | src 侧免去 222 处改动，且能把"编译期正确、运行期崩"变成 build 期失败 |
| **质量** | 测试框架用 **Node 原生 `node:test`**，**零新增依赖** | 实测 23 个用例全绿、3.4 秒跑完、覆盖率/JUnit 全是内置 flag           |
| **产品** | 只挑"能为降本服务"的通用模块，其余一律推迟           | 基座的价值是降低二次开发成本，不是功能数量                           |

**三方高度一致的判断**：这是本项目最值得高兴的一点——架构与 QA 独立得出了相同的 devDependency 结论（用 `node:test`，一个包都不装），因此**"零依赖约束"根本不需要破例讨论**。

## 2. ⚖️ 冲突裁决（主理人裁定）

### 2.1 P0-1 生产启动修复：采纳方案 C，QA 的告警不成立

QA 提出："若选 `#/*` subpath imports（方案 A），可能让 `tsconfig-paths` 失效从而使测试链路整体崩。"

**裁决：不构成冲突，因为架构推荐的就是方案 C，而方案 A 被明确排到了第二阶段。** 方案 C 完全不动 `src/` 和 `tsconfig.json`，`ts-node` + `tsconfig-paths` 的测试链路零影响。

| 方案                    | src 改动                        | 新增件           | dev 链路风险                                        | 能否 build 期拦截        | 结论      |
| ----------------------- | ------------------------------- | ---------------- | --------------------------------------------------- | ------------------------ | --------- |
| A `#/*` subpath imports | 58 文件 208 处 + gen 模板 14 处 | 0                | ⚠️ **高**（可能回退加载 dist 旧产物）+ 威胁测试链路 | 难                       | 推迟到 S2 |
| B 全量相对路径          | 222 处                          | 0                | 无                                                  | ESLint 可拦              | 备选      |
| **C 构建后别名重写** ⭐ | **0**                           | 1 脚本（~60 行） | **无**                                              | **✅ 自检 exit 1**       | **采纳**  |
| D dist 内软链           | 0                               | 1                | 无                                                  | 无（Windows/容器不可靠） | 否决      |

**落地方式**：新增 `api/scripts/rewrite-alias.mjs`，`package.json` 的 `build` 改为 `tsc -p tsconfig.json && node scripts/rewrite-alias.mjs`（只改 1 行）。

<details>
<summary>验证三条硬指标（必须全绿才算修完）</summary>

1. `npm run build && npm start` 退出码 0，且 `curl :3000/api` 返回 200
2. `grep -rc 'require("@/' dist` 残留 = **0**（实测修复前为 167 处 / 84 个 js）
3. `npm run dev:api` 仍正常启动

> 📌 若未来要迁移到方案 A，必须先跑 QA 给的 5 分钟验证配方（见 ROADMAP-QUALITY.md §9.1），确认 `tsconfig-paths` 仍生效。

## 4. 质量门禁体系（QA 实测给出）

**采纳"棘轮 + 阶梯"而非拍脑袋的绝对覆盖率目标**——这一点很关键。

| 类型                    | 规则                                                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **红线**（不可协商）    | Tier-0 六组用例 100% 通过 + 架构守卫通过 + `tsc`/`vue-tsc` 0 error + lint 全绿 + **每条 P0/P1 修复必须 1:1 带回归用例**                                        |
| **棘轮**（第 1 天生效） | 覆盖率相对上次合入**下降不得 >1%**（只增不减，比绝对目标有效得多）                                                                                             |
| **阶梯**                | S0（1-2 周）不设门槛 → S1（3-6 周）核心 7 文件行 ≥60%/分支 ≥50% → S2（2-3 月）api/src ≥45%、核心 ≥75%/65% → S3（4-6 月）api/src ≥60%、核心 ≥85%/75% + 5 条 E2E |

**实测基线**（9 个核心文件，当前 45.69% 行覆盖）：`permission.ts` **100/100/100**、`tree.ts` 91.57/89.47/90、`operationLog.ts` 44.53/66.67/37.5、`auth.service.ts` 26.67/100/10

**最先该测的 Top5**（按"出问题代价 × 概率"排序）：

1. **权限判定 `requirePermission`**（20 分）：空码 fail-closed 403、无 user 401、超管直通、viewer 用只读码访问写接口 403
2. **`operationLog` 留痕规则**（20 分）：实测 22 条写路由中 **4 条无留痕**（gen×3 + logs/http×1），正好对应 P0-2
3. **JWT 双 Token 刷新**（16 分）：access↔refresh 密钥隔离互斥校验、篡改签名失败、过期 TokenExpiredError
4. **架构守卫**（15 分）：静态扫描断言——非 auth/dashboard 路由必带 `requirePermission`、`requirePermission()` 空参数量 === 0、写接口权限码不得含 `:list`/`:query`、viewer 种子不得含写码
5. **菜单树构建**（12 分）：sort/id 双排序、父节点缺失降级为根、F 按钮不进下发树

**钩子改造**（防"类型错误推上远端"的历史事故重演，这条教训已经发生过一次）：

- `pre-commit` 追加**增量** `tsc`/`vue-tsc`
- `pre-push` 无条件全量 `tsc` + `vue-tsc` + 测试（`.husky/_/pre-push` 已存在，无需重装 husky）

> ⚠️ Windows 实测坑：npm scripts 坚持用 CLI 形态 `--require ts-node/register/transpile-only`，**不要**用 `NODE_OPTIONS`（cmd.exe 下会挂）；集成测试必须 `await sequelize.close()`，否则连接池 idle=10000 会挂满 10 秒（实测 11.8s → 3.0s）。

## 5. 建议确立的技术原则

前任已经立了 5 条权限红线（见 HANDOVER.md §5.1）。建议再补 5 条技术原则，每条都在防一个已发生或高概率的风险：

1. **自研件必须自带自检断言** —— 防 P0-1 复发（`@/` 策略编译期看着对、构建期无断言，直到 `npm start` 才崩）
2. **权限判定前后端一律 fail-closed + 写操作独立码** —— 防 P0 越权事故复发（后端已 fail-closed，前端仍 fail-OPEN，策略相反就是温床）
3. **任何新增落库/落盘数据必须同时提交清理能力** —— 防 `sys_http_log` 8.6GB/天 撑爆磁盘
4. **devDependency 新增量保持为 0** —— 三条线独立验证过可行性（`node:test` 已足够），这条让"要不要引包"永远是 5 秒的决策
5. **不改已有约束的边界，只在其内做事** —— 零依赖是约束不是负担，自研 != 不好，但要补自检
