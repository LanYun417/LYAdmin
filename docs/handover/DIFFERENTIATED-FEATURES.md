# LYAdmin 差异化后台功能推荐（决策人版）

> 撰写：高见远（架构师）｜日期：2026-09-25
> 性质：**只读盘点 + 方案建议**，除本文件外未改动任何源码与既有文档。
> 硬约束：**零第三方运行时依赖**；凡需新依赖者一律标注替代方案，否则不建议。

---

## 0. 一句话筛选标准

只做 **"本系统已有独特资产能直接支撑、而主流后台架构上无法自然生长"** 的能力。判据三条，缺一即淘汰：
① **有资产**（能落到具体文件/表/机制，不是凭空想象）；
② **架构独有**（若依 RuoYi / Ant Design Pro / Django Admin 因架构不同而做不出、或做起来别扭）；
③ **零依赖**（不引入第三方运行时依赖，必要时用平台原生能力替代）。
每项的统一形态：把某个**已有机制**从"能用"升级为 **可对账 / 可回滚 / 可预演**。

### F1. 生成物生命周期治理（血缘台账 + 漂移检测 + 一键回滚）

- **核心价值**：gen 会**不可逆地改写真实源码**（写 7 文件 + 向 5 个文件注入），一旦选错表/选错 `moduleName`，只能靠 git 或手工回退。建立"每次生成 = 一条 manifest（表→模块→文件清单→注入点+注入块哈希）"，支持漂移检测与一键回滚。目标：把 gen 从"高危写手"变成"可撤销操作"。
- **适用场景**：开发者误用已存在的 `businessName` 覆盖既有模块；上游改表结构后重新生成；接手人想搞清"这个文件是哪次生成写的"。
- **与现有系统的契合点**：`gen.writer.ts:createGenCode` 已返回 `written`/`injected`/`manualSteps`，注释明写"锚点缺失则不做半截改"——只需把每次生成固化成 manifest（新增 `services/gen.lineage.ts` + JSON 落盘）；回滚靠 `[GEN-ANCHOR]` 定位并逆插入。
- **差异化论证**：RuoYi gen 只把代码下载成 ZIP / 生成到独立目录，**从不修改你现有工程文件**，因此没有"注入"概念，也就不需要血缘与回滚；本系统 gen 直接写进 `api/src`、`admin/src` 并 5 处接线，这是它独有的能力也是独有的风险，必须配独有的解药。
- **实现成本**：2.5 人日（manifest 结构 + 5 处注入点逆操作 + 覆盖前 `.bak` 快照）。零依赖。
- **可量化验收**：任一次"生成到项目"后，可列出该次 `written`/`injected` 清单；对模块执行回滚后，5 处注入行与生成文件均回到生成前状态，`tsc --noEmit` 仍 0 error。

### F2. 路由 / 文档 / 权限码 / 菜单 四向一致性看板

- **核心价值**：把 `routeAudit` 现有的"路由 ↔ 文档"两向校验，扩展为"路由 ↔ 文档 ↔ 权限码 ↔ 菜单种子"四向对账，并把启动 `console.warn` 升级为可视化看板，逐条给出修复入口（跳到对应文件/菜单）。目标：上线前 0 处不一致、接手人 5 分钟内完成体检。
- **适用场景**：版本发布前体检；接手人盘点"有没有裸接口、幽灵权限码、只在文档里存在的接口"。
- **与现有系统的契合点**：`docs/routeAudit.ts` 已能枚举运行时路由（`collectRuntimeRoutes`）；`docs/catalog.ts` 每个 endpoint 带 `permission`；`seed/menu.seed.ts` 是权限码的第二来源；`middlewares/permission.ts` 是权限码消费方。四者均为结构化常量，天然可机器对账（新增 `docs/consistency.ts` + 看板页）。
- **差异化论证**：RuoYi 的接口文档（Swagger）与权限注解（`@PreAuthorize`）是**两套人工维护**的东西，无法机器对账；Ant Design Pro / Django Admin 也没有"路由 = 文档 = 权限 = 菜单"同一数据源的前提。本系统四者在源头即同一批常量，才有"四向一致"这种全局不变量的可能。
- **实现成本**：2 人日。
- **可量化验收**：看板列出四向不一致清单，条数可下降到 0；每条不一致附文件/菜单跳转入口。

### F3. 留痕覆盖率守卫（写操作 ↔ 操作日志规则）

- **核心价值**：`OPERATION_RULES` 是**路径正则表**，新增写接口极易漏挂 → 产生"有写操作、无留痕"的审计黑洞（gen 正是靠自动注入才补上这条）。启动时枚举全部写方法路由（POST/PUT/PATCH/DELETE），与规则表匹配，列出未覆盖项。目标：**未留痕的写接口数 = 0**。
- **适用场景**：合规要求"所有变更可追溯"；接手人新增接口后自检。
- **与现有系统的契合点**：直接复用 `middlewares/operationLog.ts` 的 `OPERATION_RULES` 与 `routeAudit.ts` 的运行时路由枚举；新增 `docs/auditCoverage.ts`，在 `server.ts` 启动时与 `auditDocsCoverage` 并列调用。
- **差异化论证**：RuoYi 用 `@Log` 注解在控制器逐个声明留痕、**无启动校验**，漏挂只有线上出事后才发现；本系统是集中式正则表 + 可运行时枚举路由，才具备做"覆盖率"这种全局不变量检查的土壤。
- **实现成本**：1 人日。
- **可量化验收**：对现有全部写路由跑一遍，输出"未挂 `OPERATION_RULES` 的写接口"清单；补齐后该清单为 0，且启动日志出现覆盖率一行汇总。

### F4. 权限变更影响面预演

- **核心价值**：改角色授权 / 停用菜单 / 删除权限码**之前**，先算出：会波及哪些用户、哪些按钮显隐翻转、哪些进程内缓存键失效、哪些前端路由停止注册。把"改完才发现在线用户被踢、按钮无故消失"变成"改前先知"。目标：每次权限变更前有 1 份可读影响清单。
- **适用场景**：超管调整角色授权；下线某功能模块；排查"为什么某人看不到某按钮"。
- **与现有系统的契合点**：`services/authCache.ts` 是**进程内 Map** 且已知 16 个主动失效点，可枚举受影响 `userId`；`store/modules/permission.ts` 的 `buttonPermissions` + 菜单驱动 `buildRoutes` 决定按钮与路由；`services/role.service.ts` 是变更入口。预演即"在内存里跑一遍失效 + 重建"。
- **差异化论证**：主流后台"保存即生效"，权限模型里没有可枚举的会话缓存，**无从预演**；本系统同时具备 进程内鉴权缓存 + 菜单驱动路由 + 按钮码三层，且缓存键即 userId，才具备"预演"所需的数据基础。
- **实现成本**：2 人日。
- **可量化验收**：提交一次角色授权变更前，返回"受影响用户数 / 按钮显隐变化数 / 失效缓存键数 / 停止注册路由数"四项；与变更后实测一致。

### F5. 统一审计时间线重建（取证视图）

- **核心价值**：把登录、操作、HTTP 三类日志按 `user + 时间窗` 关联成**一条时间线**，一次还原"某人某时段做了什么"。当前三类日志在三张表、三个页面，取证靠人工拼表（`sys_http_log` 已达 7.6 万行）。
- **适用场景**：安全事故复盘、异常操作排查、合规取证。
- **与现有系统的契合点**：三张日志表与 `logging/*` 均带 `userId`/`ip`/`time`，天然可 join；`dashboard.service.ts` 已有跨表聚合先例，直接扩展为时间线查询。
- **差异化论证**：RuoYi 三类日志彼此孤立、无关联视图；本系统操作日志与 HTTP 日志统一带 userId 与 ISO 时间，才使"按人重建时间线"成为低成本可能。
- **实现成本**：1.5 人日。
- **可量化验收**：给定 userId + 时间窗，返回一条按时间排序的三表合并时间线；抽样 3 个账号，时间线与三个单页记录一致。

### F6. 存储对账与孤儿治理（文件去重一致性）

- **核心价值**：内容去重（SHA-256）+ 引用计数删盘会沉淀两类异常：磁盘有物理文件却无 DB 记录（清理失败残留 / 手工删库），或 DB 记录指向缺失文件（磁盘被清）。做一次对账，列出孤儿物理文件与失效记录并一键处置。目标：磁盘占用对得上、无死链。
- **适用场景**：磁盘异常增长的定期体检；秒传去重上线后的对账。
- **与现有系统的契合点**：`services/file.service.ts` 的 `hash`/`filePath`/引用计数逻辑 + `models/File.ts` + `config.upload.dir`；扫描对象是 `uploads/` 目录与 `File` 表。
- **差异化论证**：RuoYi 文件管理是**记录的扁平 CRUD**，没有"内容去重 + 引用计数删盘"语义，架构上不会产生这类一致性问题；本系统独有的去重机制带来独有的风险，必须配独有的对账工具。
- **实现成本**：1.5 人日。
- **可量化验收**：对账报告分别列出"孤儿物理文件数"与"失效记录数"；一键处置后两者归 0，`File` 表与 `uploads/` 目录一致。

### F7. 图片变体缓存治理

- **核心价值**：`?scale=` 按需缩放会在磁盘沉淀大量变体且**当前无清单、无清理**；提供"变体清单 / 命中统计 / 一键清理 / 批量预热"。目标：缓存不无限增长、热门缩略图可预热。
- **适用场景**：磁盘容量治理；上线前预热常用头像与缩略图。
- **与现有系统的契合点**：`services/image.service.ts` 的 `buildCachePath`（缓存键规则）、`config.upload.cacheDir`、`inflight` 并发去重；治理工具直接扫 `cacheDir`。
- **差异化论证**：主流后台通常把图片处理交给 CDN / OSS，**无自建磁盘缓存**；本系统零依赖自研了缓存，才需要自配治理。命中率统计用轻量计数埋点即可（零依赖）。
- **实现成本**：1 人日。
- **可量化验收**：列出 `cacheDir` 变体总数与占用；清理后占用下降且不影响已缓存的合法请求；预热后热门图首访命中缓存。

### F8. 零依赖哨兵

- **核心价值**："零第三方运行时依赖"是本项目**身份的一部分**（自研 ZIP、自研 codegen、自研文档站），但目前**无任何自动化守护**——任何人 `npm i` 一个包即悄然破坏约束。加一道校验：扫描三处 `package.json` 的 `dependencies` 与源码 import 的非白名单模块，非白名单即拦截。目标：约束**可执行**而非口头。
- **适用场景**：提交 / 合并前；接手人 review 依赖变更。
- **与现有系统的契合点**：三处 `package.json`、已存在的 `husky`/`lint-staged` 钩子、`utils/zip.ts` 正是该约束的活标本；新增 `scripts/deps-guard`，挂到 pre-push 或启动自检。
- **差异化论证**：主流后台不但没有"依赖预算"，反而鼓励引库；本系统的约束即差异化本身，**守护约束的能力别处不会做**。这是"元规则"，只有约束型项目才需要。
- **实现成本**：0.5 人日。
- **可量化验收**：故意 `npm i` 一个包后守卫失败并阻塞；移除后通过。白名单（自研/原生）零误报。

### F9. 菜单可达性与图标注册双向巡检

- **核心价值**：菜单 100% 驱动路由，但 `resolveComponent` 找不到组件时**仅 `console.warn`**（用户看到空白页）；菜单图标若不在 `appIcons` 注册表则渲染空白；`redirect` 指向不存在路径会 404。做一次巡检：组件存在性 / 图标 ∈ 注册表 / redirect 有效性 / 反向找出"注册但未使用"的图标（可瘦身）。
- **适用场景**：新增菜单后自检；前端产物瘦身；排查"某菜单点开是空白"。
- **与现有系统的契合点**：`store/modules/permission.ts`（`resolveComponent`）、`utils/icons.ts`（`appIcons`/`appIconNames` 是唯一真源，注释明写"可选 = 已注册"）、`seed/menu.seed.ts`。
- **差异化论证**：RuoYi 图标是字符串全局注册、菜单组件缺失静默失败，**无从巡检**；本系统图标是显式注册表（key 即组件名），才可做"菜单图标 ⊆ 注册表"这类集合校验。
- **实现成本**：1 人日。
- **可量化验收**：巡检报告列出"组件缺失菜单 / 未注册图标菜单 / 无效 redirect / 未使用图标"四类；正常系统前三类为 0。

### F10. RBAC 配置版本化（快照 + diff + 回滚）

- **核心价值**：菜单树 / 角色-菜单授权 / 权限码当前**直接改库、无版本、无法回滚、无法对比**。为 RBAC 配置建立快照，支持"本周 vs 上周的权限差异"与一键回滚。目标：任何授权变更都可解释、可撤销。
- **适用场景**：授权误操作回滚；合规期"权限基线"冻结与对比；交接时输出当前权限基线。
- **与现有系统的契合点**：配置源即 `seed/menu.seed.ts` + `seed/role.seed.ts` 与 `sys_menu`/`sys_role_menu`/`sys_role` 三表；快照即导出这三表的结构化 diff（复用 `utils/tree.ts` 构树）。
- **差异化论证**：主流后台的 RBAC 配置同样是"改库即生效、无版本"；本系统因权限码/菜单本就是结构化种子数据，才可低成本建立"配置即代码"式的版本与 diff。
- **实现成本**：2 人日。
- **可量化验收**：导出两份快照可生成角色-菜单-权限码差异表；对误改回滚后权限与快照一致，`authCache` 相应失效。

### F11. 多标签页会话一致性

- **核心价值**：无感刷新目前是**单页内**实现；多标签时，一个标签登出 / 改密 / 被禁用，其它标签仍持旧 token 直到下次 401；一个标签刷新 token 后其它标签可能用旧 refresh 再刷，造成"半失效"体验。用**原生 BroadcastChannel** 同步 token 与登出事件。目标：任一标签登出 / 失效，全部标签同步回登录页。
- **适用场景**：运维 / 管理员多标签对照操作；改密或超管禁用后的会话收敛。
- **与现有系统的契合点**：`admin/src/api/request.ts`（无感刷新）、`utils/jwt.ts`（双 token + `passwordChangedAt` 全端失效语义）、`store/modules/user.ts`。
- **差异化论证**：RuoYi / Ant Design Pro 的无感刷新通常单页实现、无跨标签同步；本系统的"双 token + 改密全端失效"语义若不做跨页同步，会暴露明显的半失效体验。零依赖：`BroadcastChannel` 为平台原生。
- **实现成本**：1 人日。
- **可量化验收**：标签 A 登出后，标签 B 在 1 秒内同步回登录页；改密后多标签全部失效，无"半失效"残留。

## 3. 推荐 Top 3

1. **F1 生成物生命周期治理** —— gen 是本系统被严重低估的皇冠资产，而它当前**不可逆地写源码**（7 文件 + 5 处注入），这是已验证的真实风险。F1 直接把这个风险变成可回滚能力，杠杆最高，且**只有拥有"注入机制"的本系统做得出**。
2. **F4 权限变更影响面预演** —— 本系统的差异化栈（进程内鉴权缓存 + 菜单驱动路由 + 按钮码）制造了"改了不知影响谁"的真空，主流后台连建模都做不到。F4 是"用已有机制反哺自己"的典型。
3. **F2 四向一致性看板** —— 在**已验证可用**的 `routeAudit` 上做低成本升级（2 人日），直接服务"接手人 5 分钟信任系统"，性价比最高、风险最低。

> 为何不是 F3/F5：价值真实但更窄（一个管审计覆盖、一个管取证），且都可在 F2 的看板骨架上一并承载，不必单列为首选。

## 4. 明确不建议做（已考虑并否定）

| 想法                                                | 否定理由                                                                                                                                                |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **把一致性看板做成"自动修复 / 自动写文档"**         | 与 gen"锚点缺失即不做半截改"的纪律冲突；静默改写路由/文档会掩盖真实不一致，并引入"编译器式误伤"。应**只暴露、不自动改**，保持全系统"不半截改"的一致性。 |
| **基于 httpLog 做接口性能分位 / APM 面板**          | 属被排除的"服务监控"范畴；需时序存储与重采样，单实例场景用日志/系统工具足够；`resBody` 已重，再叠指标得不偿失。                                         |
| **运行时低代码（在线表单设计器 / 元数据驱动渲染）** | 与 gen"生成静态代码"重复投入、要维护两套；零依赖下拖拽自研成本极高；项目零测试时动态渲染出错影响全站。与既有路线图结论一致，**维持不做**。              |
