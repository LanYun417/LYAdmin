## 3. 瓶颈结论（按影响排序，均有数据支撑）

### 3.1 鉴权链路净开销（本次最重要产出）

**定义**：净开销 = 有鉴权接口 P95 − 无鉴权 `/api` P95（同一并发档）。

| 并发 | `/api` P95 | `/api/auth/profile` P95 | **鉴权净开销** | profile RPS | /api RPS | 吞吐倍数差 |
| ---- | ---------: | ----------------------: | -------------: | ----------: | -------: | ---------: |
| 1    |       0.76 |                    7.04 |   **+6.28 ms** |      202.28 |  1753.02 |       8.7× |
| 10   |       4.89 |                   70.80 |  **+65.91 ms** |      240.25 |  4640.12 |      19.3× |
| 50   |      13.17 |                  229.50 | **+216.33 ms** |      304.76 |  5549.87 |      18.2× |

> **鉴权净开销（P95）：并发 1 → 6.28 ms；并发 10 → 65.91 ms；并发 50 → 216.33 ms。**
> 该开销随并发线性放大，是**每一个**鉴权请求的固定成本，与业务逻辑无关。

### 3.2 每请求 SQL 条数表（证实/推翻「loadAuthUser 每请求 2~3 次 SQL」假设）

方法：记录 `logs/db/YYYY-M-D.log` 行数 → 发**单个**请求 → 等待落库 → 再计数，差值即该请求 SQL 条数。

| 接口                       | 每请求 SQL 条数 | SQL 明细                                                                                                                           |
| -------------------------- | --------------: | ---------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api`                 |           **0** | 路径 `/api` 不匹配 `/api/` 前缀，**不写访问日志**，纯框架基准                                                                      |
| `GET /api/auth/profile`    |           **3** | ① `User+Role` 联查（authenticate 中间件）② **同一条 `User+Role` 联查（controller 再次调用 loadAuthUser）** ③ `INSERT sys_http_log` |
| `GET /api/users`           |           **4** | ① `User+Role` 联查（loadAuthUser）② `count(DISTINCT)` ③ 分页 `User` 联查 `Role` ④ `INSERT sys_http_log`                            |
| `GET /api/dashboard/stats` |           **6** | ① `User+Role` 联查 ②~⑤ 四个 `count(*)`（user/role/login_log/menu）⑥ `INSERT sys_http_log`                                          |
| `GET /api/logs/http`       |           **4** | ① `User+Role` 联查 ② `count(*)` ③ 分页查询 ④ `INSERT sys_http_log`                                                                 |
| `GET /api-docs`            |           **0** | 不在 `/api/` 下，不写访问日志                                                                                                      |

**结论（部分证实 + 新发现）**：

- ✅ **证实**：`loadAuthUser()`（`auth.service.ts` 115-124 行）**每个鉴权请求都实打实查库，零缓存**。对超管 `admin`，`collectPermissions` 命中 `SUPER_ADMIN_ROLE` 短路返回 `['*']`，故为 **1 次 SELECT（User LEFT JOIN Role）**。
- 🔴 **新发现（额外损耗）**：`GET /api/auth/profile` 出现**同一条 `User+Role` 联查被执行两次** —— 因为 `authenticate` 中间件调用一次 `loadAuthUser`，`getProfile` controller **又调用一次**（`auth.service.ts` 199 行）。`getPermissions` / `getUserMenus` 同理。即 profile 类接口仅鉴权就 **2 次 SQL**。
- 📌 **假设修正**：所谓「每请求 2~3 次 SQL」对**普通鉴权接口（超管）实为 1 次**；对 **profile/menus/permissions 类为 2 次**；对**非超管用户**（`collectPermissions` 额外执行 `Menu JOIN Role` 查询，`auth.service.ts` 88-100 行）亦为 **2 次**。

### 3.3 最慢的 SQL Top 5

数据源：`logs/db/2026-9-24.log`（44 MB / 94161 条，本次含历史）。慢 SQL 阈值 `LOG_SLOW_SQL_MS=200`。

| 排名 |       耗时 | SQL                                               |
| ---: | ---------: | ------------------------------------------------- |
|    1 | **259 ms** | `SELECT count(*) AS count FROM sys_menu AS Menu;` |
|    2 |     209 ms | `SELECT count(*) AS count FROM sys_menu AS Menu;` |
|    3 |     177 ms | `SELECT count(*) AS count FROM sys_menu AS Menu;` |
|    4 |     157 ms | `SELECT count(*) AS count FROM sys_menu AS Menu;` |
|    5 |     151 ms | `SELECT count(*) AS count FROM sys_menu AS Menu;` |

- 超过 200 ms 的慢 SQL 仅 **2 条**；**负载期间平均单条 SQL 耗时 6.42 ms**（空闲单请求时仅 1~4 ms）。
- **关键洞察**：`sys_menu` 仅 37 行，`count(*)` 正常应 <1 ms，却在并发 50 下飙到 **259 ms** —— 这不是查询本身的问题，而是**数据库连接池（Sequelize `pool.max = 10`）+ 每请求 1 条 `sys_http_log` INSERT 造成的排队/资源争用**波及了所有查询。**高并发下的瓶颈是「每请求固定 DB 往返」挤占连接池**，而非单条 SQL 慢。

### 3.4 日志双写的影响（`DB_LOGGING` on/off 对比，`GET /api/users`）

> 实现方式：以**环境变量** `DB_LOGGING=false` 启动服务（dotenv 不覆盖已有环境变量），**未修改 `.env`**（保持原样，`# DB_LOGGING=false` 仍为注释）。

| 接口 / 并发           | DB_LOGGING=on P95 | DB_LOGGING=off P95 |   P95 变化 |     on RPS |    off RPS |      RPS 变化 |
| --------------------- | ----------------: | -----------------: | ---------: | ---------: | ---------: | ------------: |
| `/api/users` @ c=10   |             53.96 |              51.55 |      −4.5% |     247.97 |     258.92 |         +4.4% |
| `/api/users` @ c=50   |        **250.90** |         **179.54** | **−28.5%** | **248.16** | **318.32** |    **+28.3%** |
| `/api` @ c=50（对照） |             13.17 |              13.31 |        ~0% |    5549.87 |    6209.75 | ~0%（噪声内） |

- **`DB_LOGGING=false` 使 `/api/users` 在 c=50 下 P95 降 28.5%、吞吐升 28.3%**；`/api` 无 SQL 故基本不变（对照组有效）。
- `DB_LOGGING=true` 会为**每条 SQL** 写 JSON Lines 文件**并开启 `benchmark` 计时**，在高并发下形成可观磁盘 I/O + 计时开销。
- 注意：本对比**只关闭了 SQL 文件日志**；`sys_http_log` 的**每请求 1 条 INSERT *仍然存在***（由 `appendHttpLog` 控制，不随 `DB_LOGGING` 关闭）。因此**实际日志总开销被低估**。

## 4. 优化建议（按性价比排序，含量化估算）

> 估算基于本报告实测数据外推，非精确预测，供优先级排序参考。

### 建议 1（最高性价比）：鉴权上下文进程内缓存（TTL）

- **方向**：在 `auth.service.loadAuthUser` 外层加进程内 `Map<userId, { ctx, expireAt }>` 缓存，TTL 30~60 s；角色/状态/改密变更时主动失效对应 key。
- **量化收益**：消除**每个鉴权请求 1 次 `User+Role` SELECT**（profile 类 2 次）。参照 3.4「移除每请求固定 SQL 即 +28% 吞吐」与 3.1 鉴权净开销随并发放大，**预期鉴权类接口 c=50 下 RPS 提升约 1.3~2×、P95 从 ~230 ms 降至 ~120~150 ms**。
- **风险**：状态/权限变更最多延迟一个 TTL（强制下线/改密失效窗口）；**多实例部署下各进程缓存不一致**，集群化需改用 Redis 等共享存储（与现有登录限流同为进程内方案的已知局限一致）。

### 建议 2（零风险速赢）：消除 `getProfile`/`getPermissions`/`getUserMenus` 的重复 `loadAuthUser`

- **方向**：`authenticate` 中间件已把 `req.user` 上下文挂好，controller 层改为**复用 `req.user`**（或传入已加载 context），不再二次调用 `loadAuthUser`。
- **量化收益**：`/api/auth/profile` 每请求 SQL **3 → 2**，直接砍掉 1/3 的鉴权 SQL；**预期该接口 P95 降 15~25%**。纯代码改动、无状态语义变化。
- **风险**：极低。需保证 controller 仍能拿到完整 `permissions`（中间件已写入 `req.user.permissions`）。

### 建议 3：HTTP 访问日志落库策略优化

- **方向**：`sys_http_log` 目前**每请求 1 条同步 `await HttpLog.create`**（虽 fire-and-forget，但仍占用连接池）。改为**内存队列 + 批量 flush（如每 500 ms 或每 200 条批量 INSERT）**、或**按采样率**记录、或生产环境默认关闭。
- **量化收益**：再移除每请求 1 条 INSERT，叠加建议 1 后 **DB 端点吞吐预计再 +15~30%**（已实测：仅关 SQL 文件日志即 +28%）。
- **风险**：进程崩溃时内存队列中未落库的日志会丢失（需权衡审计完整性）；采样会减少可查询样本。

### 建议 4：`/api-docs` 结果缓存

- **方向**：`renderDocsHtml()` 结果**构建一次后缓存**，后续请求直接返回；`generatedAt` 移到 `/api-docs/data.json`（或构建期固定）。如需实时，可加 ETag/短 TTL。
- **量化收益**：`/api-docs` c=10 P95 从 40 ms → **<5 ms**，RPS 提升 10× 以上；**释放每请求 ~2.9 ms 的单线程 CPU** 给业务请求。
- **风险**：极低（文档为静态内容；仅需注意 `no-store` 改为可控缓存策略）。

### 建议 5：生产环境关闭 SQL 文件日志 / `benchmark`

- **方向**：`DB_LOGGING` 生产默认 `false`，或改为**仅记录慢 SQL**（`LOG_SLOW_SQL_MS` 已有）。
- **量化收益**：c=50 下 **+28% 吞吐 / P95 −28.5%**（3.4 已实测）。
- **风险**：减少排障用的全量 SQL 追溯；可用「慢 SQL + 错误日志」折中。

### 建议 6：数据库连接池 / 实例能力

- **方向**：Sequelize `pool.max` 当前 **10**；在建议 1/3 削减每请求 SQL 后，如需进一步扩容，可评估调大 `pool.max`（如 20）或增加只读副本承接查询。
- **量化收益**：缓解 c=50 时的排队（3.3 中 37 行表 count 竟耗时 259 ms 即为排队信号）。
- **风险**：超 MySQL `max_connections`；连接数上升带来上下文切换；需与 MySQL 实例规格匹配，**收益受单实例能力上限约束**。

## 5. 测量局限（如实声明）

1. **硬件**：本机 8 GB 内存，**API 与 MySQL 同机**，二者竞争 CPU / 磁盘 / 内存，绝对数值低于独立部署环境。
2. **同机压测**：压测客户端与服务端同物理机，客户端自身消耗 CPU，可能**轻微低估**服务端真实能力。
3. **单进程单实例**：未启用 PM2 cluster / 多 worker，无法反映多核并行能力。
4. **数据量小**：初始 `sys_user=2`、`sys_menu=37`、`sys_http_log=125`，分页/聚合尚未遭遇大表，**大表下慢查询会显著放大**（本报告慢查询结论在大数据量下需复测）。
5. **未做长时间稳定性压测**：单轮压力约 69 s，**无法判定内存泄漏**，仅能说明短期无失控增长。
6. **未测写接口**：为避免污染数据、触发登录限流锁定，仅测只读 GET 接口。
7. **单次采样**：每组仅跑一轮，未取多轮中位数，存在系统噪声（如 `DB_LOGGING=off` 的 `/api` 对照组差异属噪声范围）。
8. **慢 SQL 样本少**：阈值 200 ms，全量仅 2 条超阈值，Top5 中 3 条未达阈值。
9. **日志开销被低估**：`DB_LOGGING` 开关**不控制** `sys_http_log` 的每请求 INSERT，故第 3.4 节只量化了 SQL 文件日志的开销。
