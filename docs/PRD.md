### 客户已拍板决策（本 PRD 严格遵守，不推翻）

1. **鉴权**：JWT 双 Token —— accessToken（2 小时）+ refreshToken（7 天），Authorization Header 传递，支持无感刷新与强制下线。
2. **权限粒度**：RBAC「菜单 + 按钮级」，用户—角色—菜单三段式；后端下发菜单树，前端据此动态生成路由；按钮级权限用 `v-permission` 指令控制显隐。
3. **建表方式**：Sequelize `sync` 自动建表 + 种子数据初始化（首次启动自动建表，写入超级管理员、默认角色、完整菜单树）。
4. **前端 UI**：多标签页 tagsView、面包屑、可折叠侧边栏、暗黑模式、keep-alive 缓存；**不做 i18n**。
5. **分支策略**：master（生产）+ dev（开发集成）+ feature/_、fix/_；提交与 push 由主理人负责。
6. **部署**：只提供本地启动方式。

## 二、产品目标与定位

**产品定位**：LYAdmin 是一套面向企业内部运营/管理场景的**通用后台管理基座**，通过 RBAC 权限体系与标准化管理模块，让业务方能够在同一套框架上快速接入新功能，而不必重复搭建鉴权、权限、日志、文件等基础设施。

**可衡量目标**：

| 编号 | 目标       | 衡量标准                                                                              |
| ---- | ---------- | ------------------------------------------------------------------------------------- |
| G1   | 开箱即用   | 首次启动后端自动完成建表 + 种子数据写入，前端启动后可直接用超级管理员账号登录进入首页 |
| G2   | 权限可控   | 任意页面/按钮的可见性均可由「角色—菜单」配置驱动，新角色授权后无需改前端代码即可生效  |
| G3   | 操作可追溯 | 100% 的登录行为、写操作（增/删/改）、HTTP 请求均落库或记录，可按条件检索              |
| G4   | 交互一致   | 全站统一主布局（侧边栏 + 顶部栏 + 标签页 + 内容区），错误统一走 401/403/404/500 页面  |
| G5   | 工程规范   | 提交前 lint / format 校验自动执行，commit message 符合 cz-git 规范                    |

## 三、用户角色定义

| 角色       | 标识          | 定位           | 能力范围                                                                        |
| ---------- | ------------- | -------------- | ------------------------------------------------------------------------------- |
| 超级管理员 | `super_admin` | 系统最高权限者 | 拥有全部菜单与按钮权限；可管理用户/角色/菜单；可查看全部日志；不受权限裁剪      |
| 普通管理员 | `admin`       | 业务运营管理者 | 由超管授权部分菜单；可对授权范围内模块做增删改查；无系统级配置（角色/菜单）权限 |
| 只读访客   | `viewer`      | 数据查看者     | 仅拥有查看类菜单与按钮权限；所有写操作按钮不可见；不能修改任何数据              |

> 说明：角色与权限均由「角色—菜单授权」动态决定，以上为默认种子角色。角色可扩展，菜单授权可自定义。

## 六、关键业务流程

> 以下为需求侧的业务期望流程，具体实现方案由架构师决定。

### 6.1 登录与鉴权流程

1. 用户在登录页输入账号 + 密码，前端提交登录请求。
2. 后端校验账号是否存在、是否被禁用、密码是否正确。
3. 校验通过 → 签发 accessToken（2h）+ refreshToken（7d）并返回用户基础信息；同时写入一条登录日志（成功）。
4. 校验失败 → 返回明确错误信息，并写入一条登录日志（失败，含 IP / User-Agent）。
5. 前端保存 Token，跳转首页并按权限加载菜单。

### 6.2 无感刷新与强制下线流程

1. 业务请求携带 accessToken；若后端返回 401（Token 过期）。
2. 前端用 refreshToken 请求刷新接口换新 Token，并**重放原请求**，用户无感知。
3. 若 refreshToken 也失效 → 清除本地状态，跳转登录页并提示重新登录。
4. 若账号被禁用/改密导致 Token 失效 → 后端返回 401，前端强制登出（强制下线）。

### 6.3 权限加载与动态路由流程

1. 登录成功后，前端请求"当前用户信息 + 菜单树"接口。
2. 后端依据用户的角色 → 角色关联菜单 → 返回有权限的菜单树（含目录/菜单/按钮）。
3. 前端将菜单树映射为动态路由并注册，侧边栏据此渲染。
4. 页面内的操作按钮通过 `v-permission="'xxx:yyy'"` 与用户按钮权限码比对，决定显隐。
5. 用户直接访问无权限路由 → 进入 403 页面。

### 6.4 写操作日志流程

1. 用户发起任一写操作（新增/编辑/删除/授权等）。
2. 后端中间件拦截，记录模块、动作、请求方法、URL、参数、耗时、结果。
3. 操作完成后异步落库至操作日志表；敏感字段（如密码）脱敏存储。

## 七、页面清单与 UI 描述

### 7.1 整体布局结构

```
┌───────────────────────────────────────────────────────────┐
│  顶部栏 Topbar：折叠按钮 · 面包屑 · 右侧(暗黑模式/全屏/头像下拉) │
├────────────┬──────────────────────────────────────────────┤
│            │  标签页 tagsView：已打开页面标签，可关闭/切换    │
│  侧边栏     ├──────────────────────────────────────────────┤
│  Sidebar   │                                              │
│  (菜单树,   │           内容区 Content                      │
│   可折叠)   │      <router-view> + keep-alive 缓存          │
│            │                                              │
└────────────┴──────────────────────────────────────────────┘
```

- 侧边栏：由后端菜单树渲染的多级菜单，支持折叠；当前路由高亮。
- 顶部栏：左侧折叠按钮 + 面包屑；右侧暗黑模式开关、全屏、用户头像下拉（个人中心/退出登录）。
- 标签页：每访问一个菜单生成标签，支持切换、关闭、关闭其他。
- 内容区：路由出口，配合 keep-alive 保留页面状态。

## 九、数据实体清单

| 表名                | 中文名         | 关键字段                                                                                                                                        | 表间关系                                                                             |
| ------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `sys_user`          | 用户表         | id、username(唯一)、password(加密)、nickname、avatar、email、phone、status(启用/禁用)、last_login_at、created_at、updated_at                    | 多对多 → `sys_role`（经 `sys_user_role`）                                            |
| `sys_role`          | 角色表         | id、role_name、role_code(唯一)、sort、status、remark、created_at、updated_at                                                                    | 多对多 → `sys_user`（经 `sys_user_role`）；多对多 → `sys_menu`（经 `sys_role_menu`） |
| `sys_menu`          | 菜单权限表     | id、parent_id、menu_name、menu_type(目录/菜单/按钮)、path、component、icon、permission(按钮标识)、sort、visible、status、created_at、updated_at | 自关联（parent_id → id）形成菜单树；多对多 → `sys_role`（经 `sys_role_menu`）        |
| `sys_user_role`     | 用户角色关联表 | id、user_id、role_id                                                                                                                            | 关联 `sys_user` 与 `sys_role`                                                        |
| `sys_role_menu`     | 角色菜单关联表 | id、role_id、menu_id                                                                                                                            | 关联 `sys_role` 与 `sys_menu`                                                        |
| `sys_login_log`     | 登录日志表     | id、username、ip、user_agent、status(成功/失败)、message、login_at                                                                              | 逻辑关联 `sys_user.username`                                                         |
| `sys_operation_log` | 操作日志表     | id、user_id、username、module、action、method、url、params、duration(ms)、result(成功/失败)、ip、created_at                                     | 逻辑关联 `sys_user`                                                                  |
| `sys_file`          | 文件表         | id、origin_name、file_name、file_path、file_url、mime_type、size、uploader_id、created_at                                                       | 逻辑关联 `sys_user`(uploader_id)                                                     |

**关系概览**：

- 用户 ↔ 角色：多对多（`sys_user_role`）
- 角色 ↔ 菜单：多对多（`sys_role_menu`）
- 菜单：自关联树（`parent_id`）
- 日志/文件：记录操作主体，逻辑外键指向用户
