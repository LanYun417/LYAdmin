# 00 - 导读

本目录是 LYAdmin 仓库的 **Git 提交规范**，与 [`前端开发规范`](../前端开发规范/00-导读.md)、[`后端开发规范`](../后端开发规范/00-导读.md) 并列，属于**跨端横向规范**：只要改动本仓库（根配置、`ly-admin-web/`、`ly-admin-api/`、`knowledge/`、`scripts/`），都适用。

## 为什么单独成册

提交规范约束的是「仓库」而不是某一端：前端与后端共用同一套 commitlint 配置、同一组 husky 钩子、同一条 `main` 分支。把它写进任一端都会让另一端的读者以为与自己无关，也让「改提交信息规则」这类改动找不到唯一归属。

- 前端规范只保留「钩子如何跑 lint-staged」这类与前端工具链相关的实现细节。
- 后端规范只保留「提交前要跑哪些后端门禁」。
- 提交信息的格式、类型、分支与发布约定，统一以本目录为准。

## 硬性约定（违反即被钩子拒绝）

- 提交信息必须符合 Conventional Commits：`type(scope): subject`，首行不超过 **100** 字符。
- `type` 只能取 [01-提交信息规范](./01-提交信息规范.md) 列出的值；`subject` 统一中文、祈使句、结尾不加句号。
- 禁止 `git commit --no-verify` / `git push --no-verify` 绕过钩子。
- 分支从 `main` 切出；主分支约定为受保护（实际保护规则需在两个远端各自开启）。
- 仓库是**双远端**：`origin` = Gitee（主远端，upstream 源）、`github` = GitHub 镜像；
  推送用 `git pushall`（详见 [02-分支与发布](./02-分支与发布.md)）。
- 一次提交只做一件事：重构与功能、格式化与逻辑改动不得混在同一次提交里。

## 验收清单

- [ ] `git log --oneline -10` 中每条提交都符合 `type(scope): subject`
- [ ] 根目录 `npm install` 后 `.husky/pre-commit`、`.husky/commit-msg`、`.husky/pre-push` 均已装配
- [ ] 故意提交一条 `update` 能被 commitlint 拒绝
- [ ] `npm run guard:deps` 在 push 前自动执行且通过
- [ ] 发版 tag 形如 `v1.2.0`，发布提交形如 `chore(release): v1.2.0`
