# 01 - 提交信息规范

依据：[Conventional Commits](https://www.conventionalcommits.org/)。提交信息由 `commit-msg` 钩子 + commitlint 强制校验，不合规直接拒绝提交。

## 1. 提交格式

```txt
<type>(<scope>): <subject>
                                  ← 空行
<body>
                                  ← 空行
<footer>
```

- header（首行）必填，不超过 **100** 字符（`commitlint.config.cjs` 的 `header-max-length: 100`）。
- body 每行不超过 **100** 字符（继承自 `@commitlint/config-conventional` 的 `body-max-line-length`）；footer 同此约束。
- body、footer 可选；写 body/footer 时与 header 之间必须空一行。

## 2. type 类型

| type       | 含义           | 何时使用                                  |
| ---------- | -------------- | ----------------------------------------- |
| `feat`     | 新功能         | 用户可感知的新能力                        |
| `fix`      | 修复缺陷       | 修 bug                                    |
| `docs`     | 文档变更       | 只改文档（含 `knowledge/`、`README.md`）  |
| `style`    | 代码格式       | 缩进、分号等，**不改逻辑**                |
| `refactor` | 重构           | 既非新功能也非修 bug 的代码调整           |
| `perf`     | 性能优化       | 以性能为目的的改动                        |
| `test`     | 测试           | 新增/修改测试                             |
| `build`    | 构建系统或依赖 | vite / nest 配置、`package.json` 依赖变更 |
| `ci`       | CI 配置        | 流水线                                    |
| `chore`    | 杂项           | 不属于以上任何一类                        |
| `revert`   | 回滚           | 回滚某次提交                              |
| `wip`      | 进行中         | 临时提交，合并前需整理为正式 type         |
| `workflow` | 工作流         | 流程 / 脚本调整                           |
| `types`    | 类型           | 仅类型声明变更                            |
| `release`  | 发版           | 版本发布相关                              |

> 类型清单由 `commitlint.config.cjs` 的 `type-enum` 定义；`wip` / `workflow` / `types` / `release` 是通用集之外的仓库扩展。`npm run commit`（cz-git）默认列出常用的 11 种，其余可直接手写。

## 3. scope 范围

scope 表示改动影响的模块，用英文小写，可省略。仓库级词表：

| scope     | 对应范围                           |
| --------- | ---------------------------------- |
| `api`     | `ly-admin-api/`（后端整体）        |
| `web`     | `ly-admin-web/`（前端整体）        |
| `gen`     | 代码生成器（前后端生成模板与落盘） |
| `docs`    | `knowledge/`、`README.md`          |
| `config`  | 根工程配置（eslint / tsconfig 等） |
| `deps`    | 依赖与锁文件                       |
| `tooling` | `scripts/`、husky 钩子             |
| `release` | 发版                               |
| `root`    | 跨端且无法归入以上类别             |

后端也可直接写模块名（如 `fix(users):`、`feat(gen):`），前端可写页面域（如 `fix(login):`）。cz-git 支持逗号分隔的多 scope（`feat(api,web):`）。

## 4. subject 写法

- **统一使用中文**（中英二选一，本项目定为中文）。
- 祈使句、简短精炼，说清「做了什么」，如「新增订单导出功能」。
- 结尾**不加句号**；首行整体不超过 100 字符。
- `subject-case` 已关闭（`[0]`），中文不受大小写规则限制。

## 5. body 与 footer

- body 说明**为什么改**、影响面、取舍；不复述代码。
- footer 用于关联 issue、标注破坏性变更、注明评审例外。
- 关联 issue：

```txt
fix(users): 修复登录过期后未跳转的问题

Closes #123
```

## 6. 破坏性变更

footer 中以 `BREAKING CHANGE:` 开头，说明破坏了什么、如何迁移；header 可加 `!` 强调。

```txt
feat(api)!: 统一成功响应状态码为 200

BREAKING CHANGE: POST 接口不再返回 201，调用方若按 201 判断成功需改为 200。
```

## 7. 正确 vs 错误示例

| 判定 | 提交信息                                     | 说明                        |
| ---- | -------------------------------------------- | --------------------------- |
| ✅   | `feat(users): 新增用户头像上传`              | 完整 type + scope + subject |
| ✅   | `fix(api): 修复守卫重复跳转`                 |                             |
| ✅   | `docs: 补充自动导入章节 FAQ`                 | scope 可省略                |
| ✅   | `refactor(web): 抽取 OrderListView 复用组件` |                             |
| ✅   | `chore(deps): 更新依赖基线`                  | 依赖变更（配合 deps-guard） |
| ❌   | `update`                                     | 无 type                     |
| ❌   | `fix: 修bug。`                               | subject 带句号 / 无信息量   |
| ❌   | `Feat(users): 新增功能`                      | type 必须小写               |
| ❌   | `feat: 改动了很多东西`                       | 描述无信息量                |
| ❌   | `新增订单页`                                 | 缺 type                     |

## 8. 交互式提交

```bash
git add -A
npm run commit    # cz-git 引导选择 type → scope → subject → body → breaking
```

提交前会自动经过 `pre-commit`（lint-staged）与 `commit-msg`（commitlint）两道钩子，见 [03-提交钩子与校验链](./03-提交钩子与校验链.md)。
