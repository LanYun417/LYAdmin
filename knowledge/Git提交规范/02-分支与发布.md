# 02 - 分支与发布

## 1. 分支模型

| 分支        | 职责             | 规则                                      |
| ----------- | ---------------- | ----------------------------------------- |
| `main`      | 主分支（受保护） | 生产代码；仓库默认分支                    |
| `feature/*` | 功能分支         | 从 `main` 切出，如 `feature/order-export` |
| `fix/*`     | 修复分支         | 从 `main` 切出                            |
| `hotfix/*`  | 紧急修复         | 从 `main` 切出，修完合回 `main`           |

- 主分支是 `main`。历史遗留的 `master`（以及早期的 `dev`）已于 2026-10 更名 / 删除，
  **本地若还有 `origin/master` 之类的引用，`git fetch --prune` 清掉**，别再往上推。
- 约定上主分支受保护、改动走 PR；但**当前 Gitee 与 GitHub 两侧都还没开分支保护**
  （`protected: false`），所以直接 push 是能成功的——由人来守规矩，别把它当"已经拦住了"。
- 分支名用小写英文与连字符，不加日期前缀（提交历史本身带时间）。
- 一个分支只做一个主题；跨端的联动改动（如接口契约变更）允许在同一分支同时改 `ly-admin-api/` 与 `ly-admin-web/`。

## 2. 双仓库（Gitee + GitHub）

同一个仓库推到两个远端，`main` 分支在两边保持一致：

| 远端     | 地址                                       | 角色                                   |
| -------- | ------------------------------------------ | -------------------------------------- |
| `origin` | `https://gitee.com/lanyun417/ly-admin.git` | **主远端**：fetch / pull / upstream 源 |
| `github` | `https://github.com/LanYun417/LYAdmin.git` | 镜像远端：只推不改，给 GitHub 侧 CI 用 |

### 2.1 推送

```bash
git pushall          # = git push origin main && git push github main（仓库内已配别名）
```

单推某一边（排查时用）：

```bash
git push origin main
git push github main
```

- **`main` 的 upstream 只指向 `origin/main`**（Gitee）。`git pull` / `git status` 的对齐基准就是它；
  不要把 upstream 设成 `github/main`，否则以后不带参数的 `git push` 会推到 GitHub、Gitee 悄悄落后。
- **只在 `origin` 上 fetch**（`git fetch --prune origin`），GitHub 仅作镜像，不参与合流。
- **tag 也要两边推**：`git push --tags origin && git push --tags github`
  （`pushall` 只推分支；发版时别只推了一边）。

### 2.2 为什么给 `origin` 挂两个 pushurl 不推荐

`git remote set-url --add --push origin <url>` 能让 `git push` 一次推两个远端，但：

- 它按顺序执行，**第二个失败时第一个已经成功了**，命令退出码非 0 却分不清是哪边没成；
- `git push -u` 绑定的 upstream 语义也会变得含糊。

两个独立 remote + 别名，失败能直接看出是哪一边，代价只是多记住一个 `pushall`。

### 2.3 首次在新克隆 / 新机器上配置

```bash
git remote add github https://github.com/LanYun417/LYAdmin.git
git config alias.pushall '!git push origin main && git push github main'
```

推送凭据：Windows 走 Git Credential Manager（首次会弹浏览器登录）；
若用 PAT，注意 token 需要 `workflow` 权限，否则包含 `.github/workflows/` 的推送会被拒。
网络受限时给 GitHub 单独配代理：`git config --global http.https://github.com.proxy http://127.0.0.1:<port>`。

## 3. 提交粒度

- **一次提交只做一件事**：功能、重构、格式化、依赖升级分开提交，便于 review 与 revert。
- 重构不夹带行为变更；若必须同时进行，先提交行为不变的机械改动，再提交逻辑调整。
- 生成物与源码分开：Prisma Client 重新生成（`chore(api):`）不要混进业务改动。
- 临时提交用 `wip:`，合并前用 `git rebase -i` 整理为正式 type（不要留下 `wip` 进 `main`）。

## 4. 版本发布

- tag 统一 `v` 前缀：`v1.2.0`。
- 发布提交固定 `chore(release): v1.2.0`，便于在历史中定位。
- CHANGELOG 由提交类型推导（`feat` → minor、`fix` / `perf` → patch、含 `BREAKING CHANGE` → major）。
- 仓库未内置 release-it / standard-version；需要自动化时自行加入 `devDependencies`（`devDependencies` 变化不受 `guard:deps` 拦截，但需在 PR 说明），或沿用团队既有发布流程。

## 5. 回滚

- 优先 `git revert <sha>` 生成一条可追溯的反向提交，保留原始提交历史。
- 仅在分支尚未推送、确定无他人基于该提交工作时，才允许 `git reset`。
- 回滚提交同样遵循本规范：`revert(api): 回滚 xxx`，body 写明被回滚的 sha 与原因。

## 6. PR 自检

- [ ] 提交信息逐条符合 [01-提交信息规范](./01-提交信息规范.md)
- [ ] 未使用 `--no-verify`
- [ ] 分支基于最新 `main`，无无关文件（`dist/`、`uploads/`、日志等产物不入库）
- [ ] 根目录 `npm run lint` / `npm run format:check` / `npm run guard:deps` 通过
- [ ] 改动涉及哪一端，就附上该端的门禁结果（后端见 `后端开发规范/12-工程门禁与自检`，前端见 `前端开发规范/13-ESLint与Stylelint与Prettier`）
- [ ] 推送用 `git pushall`，确认 Gitee 与 GitHub 两侧都更新（`git branch -r` 应同时有 `origin/main` 与 `github/main`）
