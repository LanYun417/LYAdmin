# 02 - 分支与发布

## 1. 分支模型

| 分支        | 职责             | 规则                                        |
| ----------- | ---------------- | ------------------------------------------- |
| `master`    | 主分支（受保护） | 生产代码；仓库默认分支                      |
| `feature/*` | 功能分支         | 从 `master` 切出，如 `feature/order-export` |
| `fix/*`     | 修复分支         | 从 `master` 切出                            |
| `hotfix/*`  | 紧急修复         | 从 `master` 切出，修完合回 `master`         |

- 仓库使用 `master`（非 `main`）作为主分支；受保护分支禁止直接 push，改动走 PR。
- 分支名用小写英文与连字符，不加日期前缀（提交历史本身带时间）。
- 一个分支只做一个主题；跨端的联动改动（如接口契约变更）允许在同一分支同时改 `ly-admin-api/` 与 `ly-admin-web/`。

## 2. 提交粒度

- **一次提交只做一件事**：功能、重构、格式化、依赖升级分开提交，便于 review 与 revert。
- 重构不夹带行为变更；若必须同时进行，先提交行为不变的机械改动，再提交逻辑调整。
- 生成物与源码分开：Prisma Client 重新生成（`chore(api):`）不要混进业务改动。
- 临时提交用 `wip:`，合并前用 `git rebase -i` 整理为正式 type（不要留下 `wip` 进 `master`）。

## 3. 版本发布

- tag 统一 `v` 前缀：`v1.2.0`。
- 发布提交固定 `chore(release): v1.2.0`，便于在历史中定位。
- CHANGELOG 由提交类型推导（`feat` → minor、`fix` / `perf` → patch、含 `BREAKING CHANGE` → major）。
- 仓库未内置 release-it / standard-version；需要自动化时自行加入 `devDependencies`（`devDependencies` 变化不受 `guard:deps` 拦截，但需在 PR 说明），或沿用团队既有发布流程。

## 4. 回滚

- 优先 `git revert <sha>` 生成一条可追溯的反向提交，保留原始提交历史。
- 仅在分支尚未推送、确定无他人基于该提交工作时，才允许 `git reset`。
- 回滚提交同样遵循本规范：`revert(api): 回滚 xxx`，body 写明被回滚的 sha 与原因。

## 5. PR 自检

- [ ] 提交信息逐条符合 [01-提交信息规范](./01-提交信息规范.md)
- [ ] 未使用 `--no-verify`
- [ ] 分支基于最新 `master`，无无关文件（`dist/`、`uploads/`、日志等产物不入库）
- [ ] 根目录 `npm run lint` / `npm run format:check` / `npm run guard:deps` 通过
- [ ] 改动涉及哪一端，就附上该端的门禁结果（后端见 `后端开发规范/12-工程门禁与自检`，前端见 `前端开发规范/13-ESLint与Stylelint与Prettier`）
