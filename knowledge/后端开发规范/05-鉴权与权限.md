# 05 - 鉴权与权限

## 1. 双 Token

| Token        | 用途              | 默认有效期 | 存储位置（前端）    |
| ------------ | ----------------- | ---------- | ------------------- |
| accessToken  | 调用业务接口      | 2h         | localStorage / 内存 |
| refreshToken | 换取新的 Token 对 | 7d         | localStorage        |

- 签发与校验都在 `JwtService`（jose，HS256）；载荷顶层为 `userId` / `username` + `iat` / `exp`。
- 两个密钥必须不同（`config.ts` 启动时校验），否则 refreshToken 可被当作 accessToken 使用。
- 刷新时校验 refreshToken 签名 + 用户状态 + 黑名单，成功后**同时换发**两个 Token。

## 2. 登录链路

`POST /api/auth/login`：

1. 图形验证码校验（`CAPTCHA_ENABLED=true` 时；单次有效，取出即删）。
2. 登录频率限制（连续失败 5 次 / 5 分钟 → 锁定 15 分钟；Redis 不可用时退化为进程内计数）。
3. 账号存在、口令匹配、账号启用。
4. 签发双 Token，更新 `lastLoginAt`，失效该用户鉴权缓存。
5. 写登录日志（成功 / 失败都写；失败不阻断登录结果）。

## 3. AuthGuard（全局）

执行顺序（任一失败即 401，且不泄露内部细节）：

```txt
取 Token（Authorization: Bearer，或静态资源场景的 ?token=）
  → 校验签名与有效期
  → 查库加载用户（含角色码、权限码，30s 缓存）
  → 用户存在？
  → 账号启用？（禁用即强制下线）
  → passwordChangedAt > iat？（改密后旧 Token 失效）
  → 是否在登出黑名单？（Redis）
  → 挂载 req.user
```

- `@Public()` 显式放行：登录、刷新、验证码、健康检查。
- `@CurrentUser()` 取 `AuthUserContext`（`userId` / `username` / `roles` / `permissions` / `deptId` / `tokenIat`）。
- 静态资源不走控制器，由 `StaticAuthMiddleware` 复用同一套鉴权逻辑。

## 4. PermissionGuard（全局）

```ts
@RequirePermissions('system:user:list')                 // 命中任一即通过
@RequirePermissions('system:menu:list', 'system:role:list') // 多码取并集
```

| 接口声明                       | 行为                                          |
| ------------------------------ | --------------------------------------------- |
| 没有 `@RequirePermissions`     | 只要求登录（个人中心、仪表盘、业务取数）      |
| 有权限码                       | 命中任一即通过；超管（`super_admin`）直通     |
| `@RequirePermissions()` 空参数 | **拒绝（403）**，属于配置缺失，按最小权限处理 |

- 权限码格式：`<域>:<资源>:<动作>`，如 `system:user:add`、`file:upload`。
- 新增接口必须在 `seed.service.ts` 的菜单种子里补充对应按钮节点与权限码，否则新库无人可用。
- 控制器上再加 `@Public()` 不会绕过 PermissionGuard 的权限判断——公开接口不要声明权限码。

### 角色授权的种子语义（重要，曾导致数据丢失）

启动种子**只负责「首次创建」角色并写授权**：`seedRole` 遇到已存在的角色会整体跳过，
绝不会每次重启都按种子定义重建——曾经的实现是「每次启动 deleteMany + 重建」，
等于把运维在角色管理里调好的授权在重启 / 部署时**静默回滚**，且没有任何提示。

由此带来两条要知道的规则：

- **菜单节点仍是增量补建的**（`seedMenu` 按 `名称 + 父级 + 类型` 去重，缺的才建），
  所以新加的菜单会出现在菜单树里，但**不会自动授权给已有角色**——需要显式授予；
- **想按种子重置某个角色的授权**：角色管理页该行的「恢复默认」按钮
  （`POST /roles/reset-menus`，复用 `system:role:assignMenu` 权限码，有操作日志，
  自定义角色会被明确跳过并回传原因）。`npm run seed` 与启动种子是同一份实现，语义一致。

## 5. 用户级额外权限（只给某一个人加 / 减权限）

改角色会波及该角色下的**所有人**；只想给某一个人加点权限、或单独收掉他的某个权限时，用这套机制。
数据模型：`sys_user_menu`（`userId` + `menuId` + `type`），`type` 为 `1` 额外授予（GRANT）/ `2` 额外撤销（REVOKE）。

有效菜单集合（**单一口径，见 `common/auth/effective-menu.ts`**）：

```
有效菜单 = (角色菜单并集 ∪ GRANT) − REVOKE
```

两处共用这一口径，否则会出现「有权限码却看不到菜单」或反之：

- `AuthUserService.collectPermissions`：取有效菜单的 `permission` 汇总成权限码（接口鉴权）；
- `MenuService.getMenusForUser`：把有效菜单构建成侧边栏菜单树（前端动态路由）。

接口（权限码 `system:user:assignPerm`）：

| 接口                   | 入参 / 出参                                                                  |
| ---------------------- | ---------------------------------------------------------------------------- |
| `GET /users/:id/menus` | 出参 `{ roleMenuIds, grantIds, revokeIds, effectiveMenuIds }`                |
| `PUT /users/:id/menus` | 入参 `menuIds` = **期望的最终有效集合**，服务端与角色集合求差得出授予 / 撤销 |

> 为什么 PUT 传「最终有效集合」而不是「grantIds / revokeIds」：前端不必知道角色基线，
> 只管把权限树的勾选结果发上来；求差逻辑集中在服务端，避免两边各算一遍、算错。

菜单树缓存：无覆盖时按「角色组合」共享；有覆盖时键追加 `||u<id>`，否则同角色不同覆盖的用户会串味。
失效：`assignUserMenus` → `authCache.invalidate(userId)`（同时清掉该用户的菜单树缓存条目）。
前端：用户管理页操作列「权限」按钮 → `UserPermissionDrawer`；树按 `effectiveMenuIds` 回填，
勾选 = 额外授予，取消角色自带项 = 额外撤销，带「角色」标签的是角色自带项。

## 6. 数据权限

`DataScopeService.getDataScope(user)` 返回判别联合：

| 返回                        | 含义           | 调用方翻译                        |
| --------------------------- | -------------- | --------------------------------- |
| `{ mode: 'all' }`           | 全部数据       | 不加过滤                          |
| `{ mode: 'dept', deptIds }` | 指定部门及下级 | `deptId in deptIds`               |
| `{ mode: 'self', userId }`  | 仅本人         | `id = userId`（或 `userId` 字段） |

计算规则：

1. 超管 → `all`；无角色 → 收敛为 `self`（fail-closed）。
2. 任一角色 `dataScope=1`（全部）→ 立即 `all`。
3. 累积「自定义部门」与「本部门及以下」的部门集合（后者以**当前登录用户**的部门为根）。
4. 部门集合非空 → `dept`（优先于 `self`）；否则有 `self` 角色 → `self`；否则兜底 `all`。

列表接口必须把结果翻译进 `where`，不能只在内存过滤（分页 total 会失真）。

部门结构按 60s 缓存整表（避免每次列表查询都全量加载 `sys_dept`）；`DeptService` 的新增 / 编辑 / 删除
会调用 `invalidateDeptCache()` 立即失效，保证数据权限按新结构计算。

## 7. 鉴权缓存（30s）

`AuthCacheService` 缓存「用户 → 角色码 + 权限码」，避免每个请求查三张表。**改动以下数据必须失效缓存**：

| 操作                                           | 失效方式                      |
| ---------------------------------------------- | ----------------------------- |
| 用户改角色 / 删除 / 改状态 / 重置密码 / 改资料 | `invalidateAuthCache(userId)` |
| **用户改额外权限（`sys_user_menu`）**          | `invalidateAuthCache(userId)` |
| 角色改菜单 / 删除角色 / 改数据范围             | `invalidateAuthCache()` 全清  |
| 菜单增删改                                     | `invalidateAuthCache()` 全清  |
| 字典 / 参数变更                                | 不需要（不参与鉴权）          |

> 菜单树按「角色组合」缓存 30s（`MenuService.getMenusForUser`）；**若该用户有额外权限覆盖**，
> 键会追加 `||u<id>`，按用户分开缓存。菜单增删改与角色授权走 `invalidate()` 全清，
> 因此上表的失效点同时覆盖菜单树。

漏掉失效会导致权限变更最多延迟 30s 生效；新增相关写接口时对照本表检查。

## 8. 在线会话与强制下线

一次登录 = 一条 Redis 会话记录，令牌里带 `sid`（access 与 refresh **共用同一个值**）：

| 键                        | 内容                                                                      | TTL                   |
| ------------------------- | ------------------------------------------------------------------------- | --------------------- |
| `auth:session:<sid>`      | 会话详情 JSON（账号 / 昵称 / IP / 归属地 / UA / 登录时间 / 最后活跃时间） | refresh 有效期 + 1 天 |
| `auth:session:user:<uid>` | 该用户的 sid 集合（用于"下线某人的全部会话"）                             | 同上                  |
| `auth:session:index`      | 全局 sid 集合（在线列表，避免 KEYS/SCAN 全库扫）                          | 同上                  |

- **强制下线的本质是"删会话记录"**：守卫发现令牌带的 sid 已无对应记录即 401，
  刷新接口同样拦截（否则客户端一刷新就复活）。这样不用给每个令牌记黑名单，也不会随刷新累积垃圾键。
- **为什么按 sid 而不是 jti**：access 每 2h 刷新一次、jti 每次都变，按 jti 记录会让在线用户一刷新就翻倍；
  sid 在登录时生成，刷新沿用它，会话身份稳定。
- **Redis 不可用的处理**（关键）：
  - 登录时 `create()` 返回 null → 签发**不带 sid** 的令牌（宁可失去会话管理能力，
    也不能出现"带了 sid 但会话没登记 → Redis 恢复后立刻 401"）；
  - 守卫只在 `redis.isReady()` 为真时校验会话存在性，否则 Redis 一挂全体用户会被登出；
  - 不带 sid 的旧令牌跳过该校验（向后兼容）。
- **"全部下线"会额外记一次用户级登出时间**（`TokenBlacklistService`），
  让没有 sid 的旧令牌也一并失效——否则运维会看到"踢了但那人还在用"。
- ⚠️ 登录成功时会**清掉登出标记**（`clearLogout`）：判定式是 `iat * 1000 <= 登出时间`，
  而 `iat` 精度是秒，"登出后同秒内重新登录"的新令牌会被误判为已失效（刚登录就被踢）。
- **监控管理**的权限码与菜单（种子见 `seed.service.ts` 的 `monitor` 目录）：

  | 菜单     | 类型              | 路径              | 权限码                                                               |
  | -------- | ----------------- | ----------------- | -------------------------------------------------------------------- |
  | 在线用户 | `C`（菜单，叶子） | `/monitor/online` | `monitor:online:list`，按钮 `monitor:online:forceLogout`（强制下线） |
  | 系统监控 | `C`（菜单，叶子） | `/monitor/server` | `monitor:server:list`                                                |

  超管角色自动获得；普通角色需在「角色管理 → 菜单授权」中勾选。
  ⚠️ 两者都是 `C` 且**不能再挂子节点**（`M` 才是容器），否则前端会把父节点降级为透传容器、
  页面 404——详见 [04-分层与模块约定「菜单层级约定」](./04-分层与模块约定.md)。

## 9. Redis 降级

| 能力       | Redis 可用               | 不可用                     |
| ---------- | ------------------------ | -------------------------- |
| 登出黑名单 | 多实例共享，登出即时失效 | 读返回「未失效」，写跳过   |
| 在线会话   | 完整会话管理 + 强制下线  | 令牌不带 sid，跳过会话校验 |
| 登录限流   | 跨实例共享计数           | 进程内 Map（单实例有效）   |
| 验证码     | 跨实例共享               | 进程内 Map（单实例有效）   |

降级**不阻断**登录与鉴权主流程；但多实例部署时必须配置 Redis，否则黑名单与限流只在单实例生效。
