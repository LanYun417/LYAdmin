# 09 - 日志与可观测

## 1. 三层日志

| 类型      | 存储                            | 写入方                         | 用途                   |
| --------- | ------------------------------- | ------------------------------ | ---------------------- |
| 登录日志  | `sys_login_log`                 | `auth.service` 登录 / 刷新失败 | 登录审计               |
| 操作日志  | `sys_operation_log`             | `OperationLogInterceptor`      | 写操作留痕             |
| HTTP 日志 | `sys_http_log` + `access-*.log` | `HttpAccessLoggerMiddleware`   | 全量访问记录、页面查询 |

三类日志都在「日志管理」页面可查询，登录 / 操作 / HTTP 均支持导出 CSV。

**CSV 导出口径（流式，2026-10-18 改造）**：

- 导出是**流式**的：服务层返回「表头 + 游标分页生成器」，控制器用 `writeCsvStream` 逐批写出，
  内存占用只与批大小（`EXPORT_BATCH_SIZE`，默认 1000）有关，不再随行数线性增长；
- 用**游标分页**（`cursor: { id }` + `skip: 1`）而不是 offset：日志表下 offset 越大越慢，
  且导出期间新写入会造成 offset 分页重复/漏行；
- **超上限先拒后导**：先按筛选条件 `count`，超过 `EXPORT_MAX_ROWS`（默认 5 万）直接返回 400
  「超过单次导出上限…请缩小时间范围」，此时尚未写响应头，前端能拿到正常 JSON 错误；
  这样避免了「下载到一个只有半截数据的 CSV 却被当成完整数据使用」；
- 表头行带 UTF-8 BOM（否则 Excel 打开中文列名乱码），行分隔符 `\r\n`；
- `res.write()` 返回 false 时必须等 `drain` 再写（背压），否则慢客户端会把数据堆在 Node 内存里；
- 前端拦截器会把 `responseType: blob` 的错误体（JSON Blob）解析回对象，
  否则业务错误文案会退化成笼统的「请求失败（400）」。

删除能力（页面与接口一致）：

- 单条：`DELETE /api/logs/{login|operation|http}/:id`；
- 多选：`DELETE /api/logs/{login|operation|http}/batch`，请求体 `{ ids: number[] }`
  （`IdsBodyDto` 校验：非空、单次上限 500 条、逐个正整数，空数组直接 400，
  避免拼出无 `where` 的删全表）；
- 权限码按类型拆分：`log:login:remove` / `log:operation:remove` / `log:http:remove`；
- HTTP 日志另有 `DELETE /api/logs/http` 清空整表（高危独立权限 `log:http:clear`，与多选删除区别开）；
- HTTP 日志的 `count` 缓存（30s TTL）在删除命中后立即整体失效，避免列表总数与实际条数不一致。

## 2. 操作日志

```ts
@Post()
@OperationLog('用户管理', '新增')
create(@Body() dto: CreateUserDto) { ... }
```

- 只对 `POST / PUT / PATCH / DELETE` 生效；`/api/auth/*` 排除（由登录日志覆盖）。
- 拦截器在 handler 执行前记录开始时间与请求体，在 `res.on('finish')` 后异步落库（fire-and-forget）。
- 失败响应也会记录：拦截 `res.json` 捕获 `message`，结果记为失败。
- 敏感字段（`password` / `token` / `secret` 等）落库前按 `SENSITIVE_KEYS` 替换为 `***`；
  请求体超过 2KB 截断。
- 日志写入失败只打 error 日志，**不影响业务响应**。

> 新增写接口时不要忘记 `@OperationLog`；漏加不会有编译错误，但审计会缺一条。

### 2.1 变更前后值（变更留痕）

「请求参数」只说明**提交了什么**，回答不了「原值是什么、这次改了什么」。因此额外采集
`before_data` / `after_data` 两个字段（各 `varchar(2000)`）：

```ts
// 服务层：查到旧数据后、写入前
recordBefore({ nickname: user.nickname, status: Number(user.status), roleIds: [...] });
// 写入成功后
recordAfter({ nickname: dto.nickname, status, roleIds: dto.roleIds ?? [] });
```

- **采集机制**：`common/log/operation-snapshot.ts` 用 `AsyncLocalStorage` 建一个按请求的快照容器，
  拦截器在 `intercept` 里创建容器并持有引用（响应结束的回调已脱离请求上下文，读不到 `getStore()`），
  服务层通过 `recordBefore/recordAfter` 往容器里写，拦截器在 `res.on('finish')` 统一落库。
  这样业务层签名不用透传 `req`。
- **覆盖范围（刻意只覆盖关键写操作）**：用户编辑、角色编辑（含数据权限部门集合）、部门/岗位编辑、
  系统参数修改。其余接口两个字段为 `null` —— **没有采集就不写占位空对象**，
  避免前端把 `{}` 当成"有留痕但为空"。
- **落库口径**：先复用 `maskSensitive` 脱敏（密码类字段 → `***`），再整体序列化；
  单侧超过 2000 字符截断并追加 `…(truncated)`（日志表是审计证据，不该被大字段撑爆）。
- **前端展示**：操作日志页「变更留痕」列 → 弹窗做**字段级对比**（取前后键并集，逐字段比对值是否相等），
  仅高亮变化的字段；不做文本 diff —— 审计关心的是"哪个字段被改了"。
- 新增可留痕接口时：在 service 里调用 `recordBefore/recordAfter` 即可，无需改拦截器与 schema。

## 3. HTTP 访问日志

`HttpAccessLoggerMiddleware` 挂在 `{*path}` 上，覆盖 `/api` 下的所有请求：

- 记录：时间、方法、URL、状态码、耗时、IP、User-Agent、操作者（守卫执行后从 `req.user` 取）。
- 成功 GET 不保留响应体（列表响应体积大，序列化 + 脱敏纯属额外开销）；失败响应与写操作仍记录。
- 落库走内存队列批量 `createMany`：满 50 条或 500ms 刷盘，进程退出前强制 flush；写失败只告警。
- 请求体 / 查询参数经递归脱敏（键名匹配 `password|pwd|pass|token|secret|authorization|credential`）
  后截断 2KB。
- 同时写 `access-YYYY-MM-DD.log` 与 `sys_http_log`；页面查询 `count` 有 30s TTL 缓存。
- 列表只返回摘要（不含 `query` / `reqBody` / `resBody`）；展开行调 `GET /api/logs/http/detail/:id` 按需加载，
  避免列表把 Text 大字段读进内存。
- `username` 过滤为**前缀匹配**（`startsWith`），配合 `@@index([username])`；不要改回 `contains`（`%x%` 无法命中索引）。
- 静态资源不计入访问日志（由静态服务链处理）。

## 4. 文件日志

`FileLoggerService` 按天写 JSON Lines：

```
logs/
├─ app-YYYY-MM-DD.log      应用日志（info）
├─ error-YYYY-MM-DD.log    错误日志（含未捕获异常堆栈）
├─ access-YYYY-MM-DD.log   HTTP 访问日志
├─ db-YYYY-MM-DD.log       慢 SQL（> LOG_SLOW_SQL_MS，默认 200ms）
└─ archive/YYYY-MM-DD/     归档后的历史日志
```

| 配置                           | 默认       | 说明                               |
| ------------------------------ | ---------- | ---------------------------------- |
| `LOG_DIR`                      | `logs`     | 日志根目录（相对 `ly-admin-api/`） |
| `LOG_ARCHIVE_HOUR/MINUTE`      | `0` / `5`  | 每日归档时刻                       |
| `LOG_ARCHIVE_KEEP_SOURCE`      | `false`    | 归档后是否保留源 `.log`            |
| `LOG_SLOW_SQL_MS`              | `200`      | 慢 SQL 阈值                        |
| `LOG_HTTP_RETENTION_DAYS`      | `7`        | HTTP 日志保留天数                  |
| `LOG_OPERATION_RETENTION_DAYS` | `180`      | 操作日志保留天数                   |
| `LOG_LOGIN_RETENTION_DAYS`     | `180`      | 登录日志保留天数                   |
| `LOG_RETENTION_HOUR/MINUTE`    | `0` / `10` | 保留清理时刻（与归档错开）         |
| `LOG_RETENTION_ENABLED`        | `true`     | 是否启用保留清理                   |

保留天数必须为正整数：`0` 会让 `cutoff = now` 从而删光整张表，`config.ts` 对非法值直接回退默认并告警。

## 5. 代码里怎么写日志

```ts
import { Logger } from '@nestjs/common';

private readonly logger = new Logger(NoticeService.name);

this.logger.log('通知已发布');
this.logger.warn('附件为空，跳过');
this.logger.error(`写入失败: ${message}`, stack);
```

- 用 Nest `Logger`（带上下文），不要 `console.log`；`config.ts` 的启动告警是唯一例外（此时 Logger 尚不可用）。
- 不打印口令、Token、密钥、完整身份证 / 手机号；需要定位时打印 id。
- 可预期的业务失败（400/404）不要打 error 日志，避免噪声；只有未捕获异常与依赖故障才记 error。

## 6. 站内通知（`sys_notice`）

给用户看的"主动提醒"，与日志的区别：日志是给排查用的（可丢），通知是给用户看的（要留）。

- **按人存一条**（`user_id` + `is_read`），而不是"公告一条 + 已读关联表"：
  收件人规模可控，而按人存能直接支持未读数、逐条已读，以及"只发给某人"的场景
  （强制下线、改密提醒），不需要额外关联表与联表。索引 `(user_id, is_read, created_at)`
  同时服务列表与未读数。
- 正文按**纯文本**存储与渲染（不接受 HTML），从源头避免存储型 XSS。
- `NoticeService.publish()` **内部吞异常**：通知是附加信息，不能因为通知表写不进去
  就让"强制下线""重置密码"这类关键操作失败。当前接入点：
  - 强制下线单个会话 / 某用户全部会话（安全提醒，告诉本人为什么被踢）；
  - 管理员重置他人密码（安全提醒，否则用户下次登录被顶掉时不知原因）。
- 收件箱相关接口（列表 / 未读数 / 已读 / 删除 / 清空）**不设权限码**：
  每条通知按 `user_id` 天然隔离，性质与"字典取数"相同；只有 `POST /notices`（发布）要
  `system:notice:add`。已读与删除都带 `userId` 条件（`updateMany` / `deleteMany`），
  否则就是越权改别人的通知。
- 列表排序：**未读在前 + 时间倒序**——收件箱里"没看的"比"新的旧的已看"更重要。
- 前端：顶栏铃铛红点（`store/modules/notice.ts` 共享未读数，页面操作后同步）与
  「系统管理 → 通知中心」页面。未读数**不做定时轮询**，挂在挂载与写操作之后。

## 7. 系统资源监控（`GET /api/monitor/server`）

管理员看的"这台机器/这个容器现在什么状况"：CPU、内存、磁盘、负载、进程内存。

### 采样机制（为什么不是"请求时现算"）

- `os.cpus()` 返回的是**开机累计时间**，单次调用算不出使用率——必须两次采样做差。
  因此 `SystemMetricsService` 在进程内起了采样器（`setInterval` 3s，**`unref()`**，
  否则测试进程会被它吊住不退出），接口只返回最近一次快照，**不随请求触发采样**；
- 首次采样只建立基线，`cpu.usage = null`（响应里 `warmingUp: true`，页面显示"采样中"）；
- 最近 120 个点（约 6 分钟）存在进程内环形缓冲，随快照一起返回，页面曲线因此"刷新不丢历史"；
- 采样失败只记日志并沿用上一次快照——监控接口自己挂掉是最不该发生的事。

### 口径：容器 vs 宿主（这条最容易骗人）

Node 的 `os.totalmem()` 读的是 `/proc/meminfo`，**在容器里拿到的仍是宿主机内存**。
容器常常被限制在几百 MB，若直接展示 os 的数字，就会出现
「页面显示 16G 用了 3G，实际 512M 就被 OOM 杀掉」——这种数字比没有数字更危险。
所以要优先读 cgroup 限制，并在响应里用 `scope` 显式标注：

| 顺序 | 数据来源                                                                     | 说明                                                                            |
| ---- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 1    | cgroup v2：`/sys/fs/cgroup/memory.max` + `memory.current`、`cpu.max`         | 容器标准形态，`max` 视为不限                                                    |
| 2    | cgroup v1：`memory/memory.limit_in_bytes`、`cpu/cpu.cfs_quota_us` + `period` | 老内核；**limit ≥ 1TiB、quota = -1 都是"不限"哨兵值**，当正常值算会得出假百分比 |
| 3    | `os.totalmem()` / `os.freemem()`                                             | 非容器环境，或 cgroup 未设限                                                    |

- `scope: 'container' | 'host'` 表明实际用的是哪一种，页面右上角有对应标签；
- 容器里 `cpu.quotaCores`（如 1.5）也会一并返回：CPU 使用率是按**宿主核数**算的，
  配额更小时会出现"只有 40% 却已经被限流"的情况，两个数一起看才不误判。
- **负载（loadavg）在 Windows 上恒为 0**，报 0 会被读成"没有负载"，因此非 Linux 明确返回 `null`，
  页面显示"当前系统不支持"。

### 网络活动（平台适配器：Linux 读文件 / Windows 起子进程）

| 平台             | 数据来源                                 | 采样间隔                | 说明                                                                   |
| ---------------- | ---------------------------------------- | ----------------------- | ---------------------------------------------------------------------- |
| Linux（含容器）  | `/proc/net/dev`                          | 与主采样同频 3s         | 文件读，微秒级；容器里读到的是自己 network namespace，即本服务真实流量 |
| Windows          | `Get-NetAdapterStatistics`（起子进程查） | **15s**（与主采样解耦） | 进程启动 0.3~0.6s，故放宽；速率按两次实际读取的时间差算                |
| 其它（macOS 等） | 不支持                                   | —                       | `supported: false` + `reason`，界面如实提示                            |

- **为什么不用 `systeminformation` 之类的库**：它们解决的是"少写代码"，不是能力缺口——
  在 Windows 上底层同样是起子进程（Node 没有原生网卡计数器 API），而库还给不了两样东西：
  `null` 语义（"没测到" vs "没流量"）与可注入的计数来源（`NET_DEV_PATH`，让非 Linux 也能测整链路）。
  完整决策记录见本节末尾。
- **排除回环**：Linux 路径显式过滤 `lo`（同机进程通信会虚高且与真实网卡重复计数）；
  Windows 的 `Get-NetAdapterStatistics` 只列真实 NDIS 适配器，天然不含环回。
- **速率可能为 `null`**（首次采样无基线、或计数器被重置）——**不当成 0**，界面显示"采样中"。
- ⚠️ **Windows 的编码坑（已踩过）**：那个命令行工具默认按**控制台代码页**输出
  （中文系统是 GBK），而 Node 按 UTF-8 解码 → 本地化网卡名变成 U+FFFD 替换字符。
  数值全对、只有名字是乱码，很容易静默上线。必须给命令加前缀
  `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8; $OutputEncoding = [System.Text.Encoding]::UTF8;`，
  并且 e2e 里有一条断言专门盯"网卡名不含 U+FFFD"（别把它当冗余删掉）。
- **不要按网卡名过滤**：名字是本地化且机器相关的（本机实测就是"以太网"/"WLAN"），
  按名字匹配换个系统语言就失效；只把它当展示标签。
- `NET_DEV_PATH` 可覆盖计数文件：非 Linux 环境做集成测试，或容器使用 host 网络命名空间时
  指向挂载进来的宿主机 `/proc/net/dev`。
- 网络单独占一张图：单位是 **B/s**，与"使用率 %"不同轴；纵轴用紧凑单位并按量级自适应。

### 为什么不引 systeminformation（决策记录）

2026-10 讨论过用它替代自研适配器，最终**不引**，理由按重要性排序：

1. **平台不对称不会消失**：Windows 上它同样每次调用起一个子进程；
   而我们 3s 采样 → 每分钟 20 个进程，开销会直接出现在自己的 CPU 曲线里（很讽刺）；
2. **速率语义更差**：它的 `rx_sec`/`tx_sec` 就是"两次调用字节差 ÷ 时间差"（与自研同一套数学），
   但首次调用返回 **`-1`**（不是 `null`）——直接进折线图就是一个巨大负尖峰；
3. **丢失可测性**：`si.networkStats()` 直接读 OS，`NET_DEV_PATH` 注入无从谈起，
   于是"Linux 那条只在生产触发的分支"在开发机上永远测不到；
4. 体积/收益不成比例：871 KB 只为一个函数（生产还根本用不上它），
   而后端 `guard:deps` 依赖基线门禁的用意就是逼每次加依赖都过一遍脑子。

另两个候选库被直接排除：`node-network-bandwidth-monitor` 把 `os`/`child_process`（Node 内置模块）
与 `mocha` 写成**运行时依赖**（会从 registry 拉同名占位包，供应链风险）；
`traffic-lens` 是 `0.0.1` 版本且内部依赖 `systeminformation`。

如果将来需要 CPU 温度、GPU、磁盘 SMART、电池等信息，`systeminformation` 的边际价值会明显上升
——那时再引（并登记进 deps-baseline）是合理的；只为网卡吞吐则不值得。

### 其它约定

- 磁盘只统计**上传目录**所在文件系统（`config.upload.dir`）：磁盘写满时最先出问题的是它；
- 接口**不记操作日志**：页面每 5s 轮询一次，记日志只会把 `sys_operation_log` 灌满噪音，
  而"读指标"没有审计价值（要留痕的是强退这类写操作）；
- 权限码 `monitor:server:list`；前端页面 `views/monitor/server/index.vue` 默认 5s 自动刷新，
  且**页面切到后台（`document.visibilityState !== 'visible'`）时自动停**，不在看不见的标签页里空打请求。

## 8. 排查路径

| 现象             | 先看                                             |
| ---------------- | ------------------------------------------------ |
| 接口 500         | `error-*.log` 的 `[UnhandledError]` 堆栈         |
| 接口慢           | `db-*.log` 的慢 SQL，再结合 `http_log.duration`  |
| 某用户看不到菜单 | 登录日志 + 操作日志（角色 / 菜单授权）+ 30s 缓存 |
| 谁改的数据       | 操作日志（模块 / 动作 / 操作人 / 参数）          |
